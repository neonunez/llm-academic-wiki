## Ejercicio 1 — Funcion recursiva `rec` en RISC-V

### Enunciado

Implementar la funcion `rec` en ensamblador RISC-V de forma **recursiva** (no iterativa), respetando la convencion de llamada de la materia. Explicar el uso de cada registro y como se preservan los valores entre llamadas. Pueden usar la instruccion `mul`.

$$rec(n) = \begin{cases} 0 & \text{si } n = 0 \\ 1 & \text{si } n = 1 \\ 2 * rec(n-1) + 3 * rec(n-2) & \text{si } n > 1 \end{cases}$$

### Resolucion

**Pseudocodigo C:**
```c
int rec(int n) {
    if (n <= 1)
        return n;
    int resultado = 2 * rec(n-1);
    int tmp = 3 * rec(n-2);
    return resultado + tmp;
}
```

**Asignacion de registros:**
- `a0` → argumento n / valor de retorno
- `s0` → preservar n (registro saved → va al stack)
- `s1` → preservar resultado intermedio 2*rec(n-1) (registro saved → va al stack)
- `t0` → constante temporal (2 o 3 segun contexto)
- `ra` → return address (debe preservarse, ya que la funcion llama a otras)

**Prologo (reserva 16 bytes en stack):**
```
12(sp) ← ra
8(sp)  ← s0
4(sp)  ← s1
```

**Implementacion RISC-V:**
```asm
rec:
    addi sp, sp, -16
    sw ra, 12(sp)
    sw s0, 8(sp)
    sw s1, 4(sp)
    # fin prologo

    li t0, 1
    bgt a0, t0, L_else_0    # si n > 1 → ir a caso recursivo
    j L_return_0             # si n <= 1 → return n (a0 ya tiene n)

L_else_0:
    mv s0, a0               # s0 = n (preservar para accesos posteriores)

    addi a0, s0, -1         # a0 = n-1
    li t0, 2
    jal rec                 # a0 = rec(n-1)
    mul s1, a0, t0          # s1 = 2 * rec(n-1)  [resultado]

    addi a0, s0, -2         # a0 = n-2
    jal rec                 # a0 = rec(n-2)
    li t0, 3
    mul a0, a0, t0          # a0 = 3 * rec(n-2)  [tmp]
    add a0, a0, s1          # a0 = resultado + tmp  [valor de retorno]

L_return_0:
    lw s1, 4(sp)
    lw s0, 8(sp)
    lw ra, 12(sp)
    addi sp, sp, 16
    ret
```

### Explicacion

El ejercicio requiere implementar recursividad en RISC-V respetando la **ABI/convencion de llamada**:

1. **Por que usar s0 y s1:** son *saved registers* — el callee debe preservarlos. Se guardan en el stack en el prologo y se restauran en el epilogo. Esto permite que el valor de `n` y el resultado intermedio sobrevivan a las llamadas recursivas (que pueden modificar cualquier registro temporal `t*` o `a*`).

2. **Por que salvar ra:** `jal rec` sobreescribe `ra`. Si no se salva antes del primer `jal`, al hacer `ret` al final se perderia la direccion de retorno del llamador original.

3. **Casos base:** `n <= 1` → retornar `a0` tal como esta (a0=0 o a0=1 corresponden al resultado correcto segun la definicion).

4. **Orden de llamadas recursivas:** primero `rec(n-1)`, el resultado se guarda en `s1` (multiplicado por 2); luego `rec(n-2)`, el resultado se multiplica por 3 y se suma a `s1`.

### Analisis de la resolucion

**Resolucion CORRECTA** (nota: Bien).

Aspectos destacados:
- Prologo/epilogo correctos: 4 palabras en stack (ra, s0, s1, y 1 slot libre para alineacion de 16 bytes).
- Uso correcto de `bgt`/`j` para bifurcar entre caso base y recursivo.
- `li t0, 2` se carga antes del primer `jal rec` para que el valor no se pierda (t0 podria ser modificado por la llamada recursiva — pero en este caso no se usa t0 dentro de rec antes de reestablecerlo, por lo que la solucion es correcta).
- El `li t0, 1` del principio se usa para el `bgt`, luego se reutiliza t0 con valor 2 para la multiplicacion.

Punto de atencion: `li t0, 2` se carga ANTES de `jal rec` pero la llamada recursiva podria modificar t0. El alumno carga t0=2 *antes* del jal, y luego usa `mul s1, a0, t0` *despues* del jal. Si la llamada recursiva modifica t0 (los t* son caller-saved), esta instruccion `mul` usaria un t0 incorrecto. Sin embargo, en esta implementacion concreta, `rec` usa t0 internamente (li t0,1 al inicio), por lo que t0 al retornar del jal NO valdra 2. 

**Correccion necesaria:** `li t0, 2` deberia ir DESPUES del `jal rec`, no antes. Aun asi el ejercicio fue calificado Bien — posiblemente el evaluador no detecto este error menor, o la rubrica no lo penalizaba.

### Chuleta

> **Funcion recursiva en RISC-V:**
> 1. Prologo: reservar stack, guardar `ra` + todos los `s*` que se usen
> 2. Casos base: comparar con `li`+`bgt`/`blt`/`beq`, retornar via `j L_return`
> 3. Caso recursivo: preservar argumentos en `s*` antes del `jal`; despues del `jal`, `a0` tiene el resultado
> 4. Epilogo: restaurar `s*` y `ra`, ajustar `sp`, `ret`
> 5. **Regla de oro:** todo lo que necesites despues de un `jal` debe estar en un `s*` o en el stack — los `t*` y `a*` son caller-saved (pueden cambiar)

### Resolucion alternativa — res_(2)

**Diferencias clave respecto a res_(1):**

1. **Multiplicacion por 2:** usa `slli s1, a0, 1` (shift left 1 = *2) en lugar de `li t0, 2; mul s1, a0, t0`. Mas eficiente.

2. **Branch del caso base:** usa `ble a0, a1, fin` (con a1=1 cargado antes) en lugar de `bgt a0, t0, L_else_0`. Logica equivalente, diferente instruccion.

3. **Uso de a1 como temporal:** res_(2) usa `a1` para cargar la constante 1 (comparacion) y luego la constante 3 (multiplicacion). Correcto: a1 es caller-saved, se carga fresco antes de cada uso.

4. **Orden en el stack:** res_(2): `ra@0(sp), s0@4(sp), s1@8(sp)`. Res_(1): `ra@12(sp), s0@8(sp), s1@4(sp)`. Ambos validos.

5. **Bug de t0 (res_(1) solamente):** en res_(1) se carga `li t0, 2` antes del `jal rec`, pero t0 es caller-saved y puede ser modificado por la llamada recursiva — la instruccion `mul s1, a0, t0` posterior podria usar un valor incorrecto de t0. Res_(2) evita este bug usando `slli` (no necesita un registro temporal para el factor 2).

**Conclusion:** res_(2) es ligeramente mas correcta en el manejo de caller-saved registers para la multiplicacion por 2.

```asm
rec:
    addi sp, sp, -16
    sw   ra, 0(sp)
    sw   s0, 4(sp)
    sw   s1, 8(sp)

    li   a1, 1
    ble  a0, a1, fin       # si n <= 1 → retornar n (a0 intacto)
    mv   s0, a0            # s0 = n
    addi a0, a0, -1
    jal  rec               # a0 = rec(n-1)
    slli s1, a0, 1         # s1 = 2 * rec(n-1)  [shift, no mul]
    addi a0, s0, -2
    jal  rec               # a0 = rec(n-2)
    li   a1, 3
    mul  a0, a0, a1        # a0 = 3 * rec(n-2)
    add  a0, s1, a0        # a0 = 2*rec(n-1) + 3*rec(n-2)

fin:
    lw   s1, 8(sp)
    lw   s0, 4(sp)
    lw   ra, 0(sp)
    addi sp, sp, 16
    ret
```

## Ejercicio 2 — Promedio de aportes para mayores de 65

### Enunciado

Dado un arreglo `aportantes` de tamano `largo` (constante). Cada elemento es una estructura de 4 bytes:
- byte 0: edad (uint8, sin signo)
- byte 1: anos de aportes (uint8, sin signo)
- bytes 2-3: pesos aportados (int16 / half word, con signo)

Calcular el **aporte promedio** de las personas con edad >= 65. El resultado debe quedar en `a0`.

### Resolucion

**Estructura:**
```c
struct Aportante { uint8_t edad; uint8_t anos; int16_t aportes; }
// acceso: 0(reg)=edad, 1(reg)=anos, 2(reg)=aportes
// cada elemento ocupa 4 bytes → incrementar puntero de a 4
```

**Pseudocodigo C:**
```c
Aportante* arr = aportantes;
int largo = largo_val;
int suma = 0, n = 0;
while (largo > 0) {
    if (arr->edad >= 65) {
        suma += arr->aportes;
        n++;
    }
    arr++;       // +4 bytes
    largo--;
}
resultado = suma / n;  // queda en a0
```

**Registros:** a0←arr | a1←largo | t0←suma | t1←n | t2←65 | t3←valor leido

**Implementacion RISC-V:**
```asm
.data
aportantes:
    .byte 66, 43
    .half 5000
    .byte 32, 4
    .half -500
    .byte 70, 40
    .half -1000
    .byte 25, 5
    .half 200
largo: .byte 4

.text
    la a0, aportantes       # a0 = &aportantes[0]
    li t0, 0                # suma = 0
    li t1, 0                # n = 0
    la a1, largo
    lbu a1, 0(a1)           # a1 = largo (byte sin signo)

while_0:
    beqz a1, end_while_0    # if largo == 0 → salir
    li t2, 65
    lbu t3, 0(a0)           # t3 = arr->edad (byte sin signo)
    blt t3, t2, else_0      # if edad < 65 → no sumar

    lh t3, 2(a0)            # t3 = arr->aportes (half word, offset 2)
    add t0, t0, t3          # suma += aportes
    addi t1, t1, 1          # n++

else_0:
    addi a0, a0, 4          # arr++ (4 bytes por elemento)
    addi a1, a1, -1         # largo--
    j while_0

end_while_0:
    div a0, t0, t1          # a0 = suma / n
fin:
    j fin                   # halt
```

### Explicacion

Puntos clave del ejercicio:

1. **Acceso a campos de la estructura:** la estructura tiene alineacion natural por byte. `edad` esta en offset 0, `anos` en offset 1, `aportes` en offset 2. Se usa `lbu` (load byte unsigned) para edad y anos, y `lh` (load halfword signed) para aportes — importante usar `lh` porque aportes puede ser negativo (int16).

2. **Avance del puntero:** cada aportante ocupa 4 bytes → `addi a0, a0, 4`.

3. **Carga de `largo`:** `largo` es una etiqueta de dato (`.byte 4`), no un inmediato. Hay que hacer `la` + `lbu` para obtener su valor. Se usa `lbu` porque `largo` es unsigned.

4. **Division:** `div a0, t0, t1` — resultado entero en a0.

### Analisis de la resolucion

**Resolucion CORRECTA** (nota: Bien).

Aspectos correctos:
- Uso correcto de `lbu` para edad (byte sin signo) y `lh` para aportes (halfword con signo).
- Offset correcto para aportes: 2 bytes desde el inicio del elemento.
- Incremento de puntero de a 4 (tamano del struct).
- La condicion `blt t3, t2, else_0` (branch if edad < 65) es correcta para filtrar edad >= 65.

### Chuleta

> **Acceso a structs en RISC-V:**
> - Cargar puntero base con `la reg, etiqueta`
> - Campos: offset manual segun tamano de cada campo anterior
> - `lbu` para uint8, `lhu` para uint16 sin signo, `lh` para int16, `lw` para int32
> - Avanzar puntero: `addi ptr, ptr, sizeof(struct)`
> - Constante en `.data`: necesita `la` + `lbu/lw` para leerla, NO es un inmediato

### Resolucion alternativa — res_(2)

**Diferencias clave respecto a res_(1):**

1. **Estructura de funcion:** res_(2) envuelve el codigo en una funcion `AporteProm` con prologo/epilogo. El alumno mismo nota que guardar `ra` "no es necesario" porque no llama a otras funciones. Res_(1) es un programa plano sin llamada a funcion.

2. **Asignacion de registros:** res_(2) usa `t0=cant_personas, t1=suma_aportes` (vs res_(1): `t0=suma, t1=n`).

3. **Avance del puntero en la rama "suma":** res_(2) avanza el puntero en dos pasos:
   - `addi a0, a0, 2` → mueve al campo `aportes` (offset 2)
   - Despues de sumar: `addi a0, a0, 2` → avanza 2 bytes mas al siguiente elemento
   - Total: 4 bytes avanzados (correcto)
   - En la rama "noSuma": `addi a0, a0, 4` directamente

4. **Etiqueta noSuma:** el alumno anota al margen que el label `noSuma` deberia estar antes de las instrucciones de avance del loop (`addi a1, a1, -1` / `addi a0, ...`). La estructura del codigo las tiene duplicadas (una vez en la rama suma y otra en noSuma), lo que es correcto funcionalmente.

5. **Ambas resoluciones son correctas.** Res_(2) es mas idiomatica como funcion; res_(1) es mas directa como programa.

## Ejercicio 3 — Datapath: instruccion `beq` y extensor de signo

### Enunciado

Dado el datapath de la instruccion `beq x4, x4, L7` en la direccion `0x100C` con codigo de maquina `FE420AE3`:

Senales del controlador: PCSrc=1, RegWrite=0, ImmSrc=10, ALUSrc=0, ALUControl[2:0]=001, MemWrite=0, ResultSrc=x

| Instruccion | Tipo | imm[12,10:5] | rs2 | rs1 | funct3 | imm[4:1,11] | op |
|---|---|---|---|---|---|---|---|
| beq x4, x4, L7 | B | 1111111 00100 | 00100 | 00100 | 000 | 10101 | 1100011 |

Preguntas:
1. Como se calcula la salida del extensor de signo.
2. Cual seria la direccion de la proxima instruccion.
3. Que funcion cumplen PCSrc, ImmSrc, ALUSrc, ALUControl[2:0].
4. Que componente define los valores de estas senales.

### Resolucion

**Extensor de signo — tipo B (ImmSrc=10):**

El inmediato tipo B se reconstruye desde los siguientes campos de la instruccion de 32 bits:

| bit instruccion | bit inmediato |
|---|---|
| inst[31] | imm[12] (signo) |
| inst[7] | imm[11] |
| inst[30:25] | imm[10:5] |
| inst[11:8] | imm[4:1] |
| — | imm[0] = 0 (siempre, instrucciones alineadas de 2 bytes) |

Para `FE420AE3`:
- inst[31]=1, inst[30:25]=111111, inst[11:8]=0101, inst[7]=1
- Inmediato (13 bits): imm[12:0] = {1, 1, 111111, 0101, 0} = 1\_1111\_1101\_010\_0

Extendido a 32 bits con extension de signo (bit12=1 → rellenar con 1s):

$$\text{ImmExt} = \texttt{0xFFFFFFF4} = -12$$

**Proxima instruccion:**

Como `PCSrc=1`, el MUX selecciona `PCTarget` (en lugar de `PCPlus4`):

$$\text{PCTarget} = \text{PC} + \text{ImmExt} = \texttt{0x100C} + (-12) = \texttt{0x100C} - 12 = \texttt{0x1000}$$

La proxima instruccion se encuentra en la posicion **0x1000** de memoria.

> Nota: PCSrc=1 porque `beq x4, x4` → x4==x4 → la ALU resta y obtiene 0 → Zero=1; y Branch=1 (determinado por el decodificador al ver opcode de `beq`). Entonces: $\text{PCSrc} = \text{Branch} \;\texttt{AND}\; \text{Zero} = 1$.

**Funcion de las senales:**

| Senal | Funcion | Valor en este caso |
|---|---|---|
| **PCSrc** | Elige el proximo valor del PC: 0=PCPlus4 (secuencial), 1=PCTarget (salto) | 1 → saltar a PCTarget |
| **ImmSrc** | Indica al extensor de signo como decodificar el inmediato segun tipo de instruccion | 10 → tipo B |
| **ALUSrc** | Origen del segundo operando de la ALU: 0=registro (RD2), 1=inmediato extendido | 0 → toma rs2 (x4) |
| **ALUControl[2:0]** | Operacion que realiza la ALU | 001 → sustraccion (para comparar igualdad: result==0 ↔ Zero=1) |

**Componente que define las senales:**

El **controlador de senales** (unidad de control), que se subdivide en:
1. **Decodificador de instruccion:** a partir del opcode `[6:0]` determina RegWrite, ImmSrc, ALUSrc, MemWrite, ResultSrc y una senal Branch.
2. **Controlador de ALU:** a partir de funct3 `[14:12]` y funct7 `[31:25]` — junto con la senal del decodificador — determina ALUControl[2:0].

Finalmente: $\text{PCSrc} = \text{Branch} \;\texttt{AND}\; \text{Zero}$ (la senal Branch viene del decodificador; Zero viene de la ALU).

### Analisis de la resolucion

**Resolucion CORRECTA** (nota: Bien).

Aspectos correctos:
- Identificacion correcta del tipo B a partir de ImmSrc=10.
- Reconstruccion correcta del inmediato B-type con los campos no contiguos.
- Calculo correcto de PCTarget = 0x100C - 12 = 0x1000.
- Explicacion correcta de cada senal y su funcion en el datapath.
- Explicacion correcta del controlador de senales (decodificador + controlador ALU).
- Correcta observacion de que PCSrc = Branch AND Zero.

### Chuleta

> **Instruccion tipo B (branch) en RISC-V:**
> - Inmediato tiene bits NO contiguos en la instruccion: imm[12|10:5] en bits[31|30:25], imm[4:1|11] en bits[11:8|7]
> - bit 0 del inmediato siempre = 0 (instrucciones alineadas a 2 bytes)
> - Extender con signo (bit12 es el signo)
> - PCTarget = PC + imm_extendido
> - PCSrc = Branch AND Zero: el salto ocurre solo si la condicion es verdadera (Zero=1 para beq)
> - ALUSrc=0 en branches → la ALU compara dos registros, no un registro con un inmediato
> - ImmSrc determina el modo del extensor de signo (00=I, 01=S, 10=B, 11=J segun convencion de la materia)

### Resolucion alternativa — res_(2)

**Diferencias clave respecto a res_(1):**

1. **Estilo de respuesta:** res_(2) es mas conceptual y textual; res_(1) es mas tecnica con tablas y formulas. Ambas alcanzan los mismos resultados numericos.

2. **Explicacion del inmediato:** res_(2) explica la concatenacion de bit 0 de forma verbal ("los bits menos significativos pasan de ser 1010=0xA a ser 0100=0x4"), llegando al mismo ImmExt = 0xFFFFFFF4 = -12.

3. **PCSrc:** res_(2) explica que la condicion `beq x4, x4` siempre se cumple porque es el mismo registro, y PCSrc=1 envia la senal al MUX de PCNext. Res_(1) explicita la formula PCSrc = Branch AND Zero.

4. **Unidad de control:** res_(2) menciona que "la unidad de control es la encargada de revisar si el flag zero esta en unos y setear (con PCSrc) si se hace el salto" — no distingue explicitamente entre decodificador de instruccion y controlador de ALU como lo hace res_(1).

**Ambas correctas.** Res_(1) tiene mayor precision tecnica; res_(2) tiene mayor claridad conceptual.
