## Ejercicio 1 — Triangulo de Pascal en RISC-V (2 pts.)

### Enunciado

Implementar en ensamblador RISC-V la funcion que calcula el valor de un elemento en un triangulo de Pascal:

```c
function pascal(fila, columna) {
    if (columna > fila) return 0;
    if (columna <= 1 || fila <= 1) return 1;
    return pascal(fila-1, columna) + pascal(fila-1, columna-1);
}
```

Explicar en que registros se almacenan los valores en cada paso y como se asegura la convencion de llamada.

### Resolucion

Convencion: `a0 = fila`, `a1 = columna`. Funcion recursiva que hace dos llamadas recursivas — requiere guardar ra y registros s.

```asm
pascal:
addi sp, sp, -32
sw   s1, 0(sp)
sw   s2, 4(sp)
sw   s3, 8(sp)
sw   s4, 12(sp)
sw   ra, 16(sp)

bgt  a1, a0, return_0   # if (columna > fila) return 0
li   t0, 1
ble  a1, t0, return_1   # if (columna <= 1) return 1
ble  a0, t0, return_1   # if (fila <= 1) return 1

# caso recursivo
mv   s1, a0             # preservo fila en s1 (s-register: sobrevive llamadas)
mv   s2, a1             # preservo columna en s2
addi a0, a0, -1         # a0 = fila - 1

jal  pascal             # pascal(fila-1, columna) — columna no cambia
mv   s3, a0             # guardo resultado parcial en s3

addi a0, s1, -1         # a0 = fila - 1 (recuperado de s1)
addi a1, s2, -1         # a1 = columna - 1
jal  pascal             # pascal(fila-1, columna-1)
add  a0, a0, s3         # a0 = pascal(fila-1, columna) + pascal(fila-1, columna-1)

j return

return_0: li a0, 0
          j return
return_1: li a0, 1
          j return

return:
lw   s1, 0(sp)
lw   s2, 4(sp)
lw   s3, 8(sp)
lw   s4, 12(sp)
lw   ra, 16(sp)
addi sp, sp, 32
ret
```

### Explicacion

**¿Por que se usan registros s?**
La funcion hace dos llamadas recursivas (`jal pascal`). Despues de la primera llamada, los registros `a0`, `a1` y los `t` pueden haber sido sobreescritos. Los registros `s` son saved-registers — la llamada a `pascal` garantiza preservarlos (si ella misma los usa, los guarda en su propio frame). Por eso `s1=fila`, `s2=columna`, `s3=resultado_primera_llamada` sobreviven a la primera llamada recursiva.

**Stack frame:**
- `sp-0`: s1 (fila original)
- `sp-4`: s2 (columna original)
- `sp-8`: s3 (resultado primera llamada recursiva)
- `sp-12`: s4 (guardado por convencion aunque no se use)
- `sp-16`: ra (direccion de retorno)
- Tamano: 32 bytes (se reservan 32 aunque se usen 20 — alineacion)

**Flujo de argumentos entre llamadas recursivas:**
1. Primera llamada: `a0=fila-1`, `a1=columna` (sin modificar a1)
2. `mv s3, a0` — captura resultado antes de que `a0` sea destruido
3. Segunda llamada: `a0=s1-1=fila-1`, `a1=s2-1=columna-1`
4. `add a0, a0, s3` — suma ambos resultados

### Analisis de la resolucion

Correcta. Manejo de convencion adecuado. Observacion: `s4` se guarda pero no se usa — costo innecesario pero no es error. Los `return` labels estan en pagina separada (carilla siguiente).

### Chuleta

> 1. Identificar si la funcion hace llamadas → si hace `jal`, necesita guardar `ra` y salvar los argumentos que se necesitan post-llamada en registros `s`
> 2. Frame: `addi sp, sp, -N` → `sw ra` + `sw sX` necesarios
> 3. Antes de cada `jal`: cargar `a0`, `a1` con los nuevos argumentos
> 4. Despues de cada `jal`: capturar resultado de `a0` en registro `s` antes de que se sobreescriba
> 5. Epilogo: restaurar todos los `s` y `ra` que se guardaron, `addi sp, sp, N`, `ret`

## Ejercicio 2 — inv e invertirArreglo en RISC-V (2 pts.)

### Enunciado

Implementar en ensamblador RISC-V respetando convencion de llamada:
- `int inv(int x) = -x` (inverso aditivo)
- `void invertirArreglo(int arr[], int largo)`: cambia cada elemento del arreglo por su inverso aditivo.

Describir el comportamiento y como se respeta la convencion.

### Resolucion

**inv** (funcion hoja — no llama a nadie):

```asm
inv:
xori a0, a0, -1     # flip todos los bits de a0 (complemento a 1)
addi a0, a0, 1      # +1 => complemento a 2 = -x
ret
```

Convencion: no usa registros manejados (s/ra), toma argumento en `a0` y devuelve en `a0`. Sin stack frame necesario.

**invertirArreglo** (`a0 = arr`, `a1 = largo`):

```asm
invertirArreglo:
addi sp, sp, -16    # frame: 4 registros × 4 bytes
sw   ra, 0(sp)      # guarda ra: hara jal a inv
sw   s1, 4(sp)      # guarda s1: usara para preservar arr
sw   s2, 8(sp)      # guarda s2: usara para preservar largo
sw   s3, 12(sp)     # guarda s3: indice

mv   s1, a0         # s1 = arr (sobrevive llamadas a inv)
mv   s2, a1         # s2 = largo (sobrevive llamadas a inv)
li   s3, 0          # s3 = indice = 0

for:
beq  s3, s2, return # if indice == largo: fin
lw   t0, 0(s1)      # t0 = arr[indice]
mv   a0, t0         # argumento para inv
jal  inv            # a0 = inv(arr[indice]) = -arr[indice]

sw   a0, 0(s1)      # arr[indice] = resultado
addi s3, s3, 1      # indice++
addi s1, s1, 4      # puntero al siguiente elemento (4 bytes por int)
j    for

return:
lw   ra, 0(sp)
lw   s1, 4(sp)
lw   s2, 8(sp)
lw   s3, 12(sp)
addi sp, sp, 16
ret
```

### Explicacion

**¿Por que se usan s1, s2, s3 en lugar de a0, a1, t?**
`invertirArreglo` llama a `inv` con `jal`. Despues de esa llamada, no hay garantia de que `a0` y `a1` conserven sus valores (son caller-saved). Si se guardaran en `t`, tampoco habria garantia. Los `s` registers son callee-saved: `inv` esta obligada a preservarlos si los modifica — y como `inv` no los usa, quedan intactos.

**Calculo del inverso aditivo:**
$-x = \overline{x} + 1$ (complemento a dos). `xori a0, a0, -1` invierte todos los bits (XOR con 0xFFFFFFFF); `addi a0, a0, 1` suma 1.

### Analisis de la resolucion

Correcta. El uso de registros `s` para preservar argumentos a traves de la llamada a `inv` es el patron correcto. La nota del alumno explica explicitamente la razon (aclaraciones ① y ②).

### Chuleta

> 1. **Funcion hoja** (no llama a nadie): sin necesidad de guardar `ra`. Solo `xori + addi` para negacion en complemento a dos.
> 2. **Funcion que llama a otra**: guardar `ra` + todos los argumentos/variables que se necesiten post-llamada en registros `s`
> 3. **Iteracion con llamadas internas**: patron → `mv sX, aY` antes del loop para preservar argumentos; indice en registro `s`; restaurar todo en epilogo

## Ejercicio 3 — Estructuras y acceso a memoria en RISC-V (4 pts.)

### Enunciado

Estructura `BalanceDeudor`:
- ID: entero sin signo de 8 bits (offset 0x0000)
- Consumos: complemento a dos de 16 bits (offset 0x0001)
- Pagos: complemento a dos de 16 bits (offset 0x0003)

Se pide:
1. Calcular bytes de la estructura y de un arreglo de 12 elementos.
2. Implementar `contarDeudores(balanceDeudores)`: cuenta elementos donde consumos > pagos. Fin del arreglo: ID nulo.

### Resolucion

**Tamano:**
- ID: 1 byte
- Consumos: 2 bytes
- Pagos: 2 bytes
- **Total: 5 bytes por estructura**
- Arreglo de 12: $5 \times 12 = 60$ bytes + 1 byte del ID nulo final = **61 bytes**

**contarDeudores** (`a0 = puntero a balanceDeudores`):

```asm
contarDeudores:
li   t0, 0          # t0 = acumulador de deudores

for:                # a0 = puntero al elemento actual
lbu  t4, 0(a0)      # t4 = ID del elemento (unsigned byte)
beqz t4, return     # if ID == 0: fin del arreglo

lh   t1, 1(a0)      # t1 = consumos (signed half, offset 1)
lh   t2, 3(a0)      # t2 = pagos (signed half, offset 3)

sub  t3, t2, t1     # t3 = pagos - consumos

bgez t3, no_hacer_nada  # if pagos >= consumos: no es deudor

addi t0, t0, 1      # es deudor: incrementar acumulador

no_hacer_nada:
addi a0, a0, 5      # avanzar al siguiente elemento (5 bytes)
j    for

return:
mv   a0, t0         # valor de retorno = acumulador
ret
```

### Explicacion

**Acceso a campos de la estructura:**
- `lbu t4, 0(a0)`: carga 1 byte sin signo (ID). `lbu` porque el ID es unsigned.
- `lh t1, 1(a0)`: carga 2 bytes con signo (consumos). `lh` porque es complemento a dos de 16 bits.
- `lh t2, 3(a0)`: carga 2 bytes con signo (pagos). Offset 3 = 1 (ID) + 2 (consumos).
- `addi a0, a0, 5`: avanza 5 bytes al siguiente elemento.

**Logica de conteo:**
`sub t3, t2, t1` calcula `pagos - consumos`. Si el resultado es negativo (pagos < consumos), el cliente debe mas de lo que pago → es deudor → incrementar. Si `bgez t3, no_hacer_nada` se cumple (resultado $\geq 0$), el consumo no supera el pago → no contar.

**¿Por que no se necesita convencion de llamada completa?**
`contarDeudores` es funcion hoja (no llama a nadie). Solo usa registros `t` (caller-saved) internamente, por lo que no necesita guardar nada en stack.

### Analisis de la resolucion

Correcta. Uso correcto de `lbu` para campo unsigned y `lh` para campos signed. Condicion de fin por ID nulo es el patron tipico de arreglos terminados en centinela. Logica del `bgez` correcta (complementaria: saltar si NO es deudor).

### Chuleta

> 1. **Acceso a campos de struct**: calcular offsets manualmente (suma de bytes de campos anteriores). Usar `lbu`/`lb`/`lh`/`lw` segun el tipo del campo.
> 2. **Arreglo terminado en centinela**: `lbu t, 0(ptr)` → `beqz t, fin` al inicio del loop
> 3. **Avanzar en el arreglo**: `addi ptr, ptr, tamano_struct`
> 4. **Conteo condicional**: calcular diferencia → `bgez`/`blez` para saltar el incremento cuando no corresponde

## Ejercicio 4 — Microarquitectura ciclo simple: instruccion `or x4, x5, x6` (2 pts.)

### Enunciado

Para la microarquitectura de ciclo simple vista en clase (RISC-V), explicar que componentes y senales de control estan involucrados y como modifican el estado del procesador al ejecutar `or x4, x5, x6`.

### Resolucion

**Componentes involucrados:**

1. **PC y Memoria de Instrucciones**: el PC apunta a la instruccion. Se lee `or x4, x5, x6` de la memoria de instrucciones.

2. **Decodificacion**: la instruccion se divide en campos:
   - OP, Func3, Func7 → Unidad de Control
   - dir(x5) → AD1 del Banco de Registros
   - dir(x6) → AD2 del Banco de Registros
   - dir(x4) → AD3 del Banco de Registros (destino)
   - El inmediato **no** se usa (no va al extensor)

3. **Banco de Registros**:
   - Lee x5 → sale por RD1
   - Lee x6 → sale por RD2
   - WE3 = 1 (se va a escribir el resultado)

4. **Mux AluSrc**: selecciona RD2 (registro x6) como segundo operando de la ALU. **AluSrc = 0** (se usa el registro, no el inmediato extendido).

5. **ALU**: recibe RD1 (x5) y RD2 (x6). **AluCon** configurado para operacion OR. Calcula `x5 OR x6`.

6. **Mux SelectRes**: selecciona la salida de la ALU como dato a escribir. **SelectRes = 0** (resultado de la ALU, no de memoria de datos).

7. **Banco de Registros (escritura)**: la salida del mux va a WD3. AD3 = dir(x4). Se escribe `x5 OR x6` en el registro x4.

**Senales de control activadas:**
- `AluSrc = 0` (segundo operando = registro)
- `AluCon = OR`
- `SelectRes = 0` (resultado = salida ALU)
- `WE3 = 1` (habilitar escritura en banco de registros)
- `MemWrite = 0` (no se escribe en memoria de datos)

**Estado modificado:**
- Registro x4 ← x5 OR x6
- PC ← PC + 4

### Explicacion

`or x4, x5, x6` es una instruccion tipo R (tres registros, sin inmediato). El datapath de ciclo simple la ejecuta en un unico ciclo de reloj. La memoria de datos no es accedida (no es load/store). La unica modificacion de estado observable es la escritura en x4 y el incremento del PC.

La nota del alumno aclara que omite el mecanismo de actualizacion del PC por no ser relevante para la pregunta.

### Analisis de la resolucion

Correcta y completa. El diagrama dibujado a mano muestra claramente el flujo de datos. Las senales AluSrc=0 y SelectRes=0 estan correctamente identificadas como criticas para distinguir esta instruccion de un load (AluSrc=1) o un store (MemWrite=1, WE3=0).

### Chuleta

> 1. **Instruccion tipo R** (op reg, reg, reg): AluSrc=0, SelectRes=0, WE3=1, MemWrite=0
> 2. **Diferencia con load** (lw): AluSrc=1 (usa inmediato extendido), SelectRes=1 (escribe dato de memoria)
> 3. **Diferencia con store** (sw): WE3=0 (no escribe en banco de registros), MemWrite=1
> 4. **Siempre involucrado**: PC, Mem instrucciones, Banco Registros (lectura), Unidad de Control, ALU
> 5. **AluCon** determina la operacion concreta: AND, OR, ADD, SUB, etc.
